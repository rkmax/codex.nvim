Goal
- Expand Codex research with deeper details on authentication flows, sandbox/approval behavior, non-interactive streaming events, built-in slash commands, and configuration defaults to inform the Neovim plugin plan.

Plan
- Review Codex docs for authentication, advanced usage (logging, MCP roles), and sandbox policies.
- Capture non-interactive (`codex exec`) behaviors, event schemas, and structured output options.
- Note built-in slash commands and quickstart tips that affect UX expectations.
- Extract key defaults and extensibility points from `example-config.md` (models, feature flags, model providers).

Findings
- Authentication: `codex login --with-api-key` reads the API key from stdin/file so it never appears in history; migrate from API key to ChatGPT by deleting `~/.codex/auth.json` and re-running login; headless flow works by copying `auth.json` from a machine where login ran or by SSH port-forwarding `localhost:1455` before login (source: https://raw.githubusercontent.com/openai/codex/main/docs/authentication.md).
- Advanced/MCP/logging: `RUST_LOG` controls verbosity; TUI logs to `~/.codex/log/codex-tui.log` with defaults `codex_core=info,codex_tui=info,codex_rmcp_client=info` while `codex exec` defaults to `RUST_LOG=error`; Codex can act as MCP client or server—`codex mcp-server` exposes `codex` (parameters: prompt, approval-policy, base instructions, config overrides, cwd, model, profile, sandbox) and `codex-reply` (prompt + conversationId) tools, usable via MCP Inspector with longer timeouts for long runs (source: https://raw.githubusercontent.com/openai/codex/main/docs/advanced.md).
- Non-interactive exec: `codex exec` defaults to read-only, no approvals; `--full-auto` allows edits, `--sandbox danger-full-access` allows edits + network; default streaming goes to stderr with only the final agent message to stdout, `-o/--output-last-message` writes final output to file; `--json` streams JSONL events (`thread.started`, `turn.started/completed/failed`, `item.started/updated/completed`, `error`) with item types `agent_message`, `reasoning`, `command_execution`, `file_change`, `mcp_tool_call`, `web_search`, `todo_list`; supports structured output via `--output-schema` (strict JSON Schema) plus optional `-o` path; requires git repo unless `--skip-git-repo-check`; resume via `codex exec resume <id|--last>` preserving conversation; `CODEX_API_KEY` env override works only for `codex exec` (source: https://raw.githubusercontent.com/openai/codex/main/docs/exec.md).
- Sandbox/approvals: Defaults to read-only until a workdir is trusted; trusting upgrades to Agent preset (workspace-write, prompts only when leaving sandbox); `--ask-for-approval never` disables prompts even in read-only; common combos documented (`--full-auto` = workspace-write + on-request approvals; `--yolo` bypasses sandbox and approvals, alias for `--dangerously-bypass-approvals-and-sandbox`); network is off in workspace-write unless enabled; platform enforcement uses Seatbelt (macOS), Landlock+seccomp (Linux), experimental restricted token (Windows) with noted limitations; helpers exist (`codex sandbox macos/linux [--full-auto] [COMMAND]...`) to probe sandbox behavior (source: https://raw.githubusercontent.com/openai/codex/main/docs/sandbox.md).
- Slash commands: Built-ins include `/model`, `/approvals`, `/review`, `/new`, `/init` (create AGENTS.md), `/compact`, `/undo`, `/diff`, `/mention`, `/status`, `/mcp`, `/logout`, `/quit`/`/exit`, `/feedback` (source: https://raw.githubusercontent.com/openai/codex/main/docs/slash_commands.md).
- Getting started/UX cues: Resume interactive sessions via `codex resume [--last|<id>]`; prompts can be passed directly (`codex "..."`); `@` triggers fuzzy file search; Esc–Esc edits previous user message; `--cd` sets workdir, `--add-dir` exposes extra writable roots; `-i/--image` attaches images; AGENTS.md lookup order: `~/.codex/AGENTS.md`, then directory chain (prefers `AGENTS.override.md` over `AGENTS.md`); example prompt scenarios illustrate Codex performing diffs/tests/migrations (source: https://raw.githubusercontent.com/openai/codex/main/docs/getting-started.md).
- Config defaults/extensibility: Example config shows defaults `model`/`review_model` = `gpt-5.1-codex-max`, `model_provider` = `openai`, reasoning knobs (`model_reasoning_effort` default `medium`, reasoning summary/verbosity controls); approval default `on-request`, sandbox default `read-only` with `sandbox_workspace_write.network_access` default `false`; feature flags under `[features]` include `unified_exec`, `rmcp_client`, `apply_patch_freeform`, `view_image_tool`, `web_search_request`, `experimental_sandbox_command_assessment`, `ghost_commit`, `enable_experimental_windows_sandbox`; tool aliases under `[tools]` (web_search, view_image); MCP server examples (stdio/http) allow env vars, headers, tool allow/deny lists, timeouts; model provider overrides for OpenAI (custom base_url, wire_api `responses`/`chat`, retries, headers, env tokens), Azure (base_url + api-version query param + env key), and OSS/Ollama (chat-compatible base_url); profiles allow named presets, projects allow trust-level hints, OTEL section shows exporter wiring (source: https://raw.githubusercontent.com/openai/codex/main/docs/example-config.md).
- Execpolicy: Supports Starlark-based `.codexpolicy` rules in `~/.codex/policy` with `prefix_rule` entries that choose allow/prompt/forbidden; Codex loads all `.codexpolicy` files on startup, validates `match`/`not_match` samples, and you can preview decisions via `codex execpolicy check --policy <file> ...`; feature is preview/unstable (source: https://raw.githubusercontent.com/openai/codex/main/docs/execpolicy.md).
- Prompts: Custom slash prompts live in `$CODEX_HOME/prompts/*.md`; filename becomes prompt name; optional YAML frontmatter (`description`, `argument-hint`); supports positional placeholders `$1..$9`, `$ARGUMENTS`, named placeholders `$FILE`, etc.; invoked via `/prompts:<name>` with named args `KEY=value` (quoted if spaces); built-in command names are hidden in the popup but still callable via `/prompts:<name>` (source: https://raw.githubusercontent.com/openai/codex/main/docs/prompts.md).
- Windows sandbox details: Windows sandbox uses restricted tokens, PATH stubs, and allowlists; known failing smoke tests include ADS write blocking (#32), `.GiT` case-variation protection (#33), PATH stub bypass check (#35), and `Start-Process https` escape (#41), leaving 37/41 passing; contributors encouraged to improve (source: https://raw.githubusercontent.com/openai/codex/main/docs/windows_sandbox_security.md).
- FAQ highlights: Clarifies modern Codex vs 2021 model; recommends GPT-5.1 Codex with `/model` to raise reasoning; `codex exec` is the automation path; to prevent edits use `--sandbox read-only` or `/approvals`; Windows not officially supported (prefer WSL2); Homebrew upgrade requires cask path if <=0.46; MCP configuration lives in `config.toml` (source: https://raw.githubusercontent.com/openai/codex/main/docs/faq.md).
- Release management: Distribution via GitHub Releases, npm (`@openai/codex`), Homebrew cask; release script `codex-rs/scripts/create_github_release` supports `--publish-alpha` or `--publish-release` with `--dry-run` to preview version; GitHub Actions publishes npm, Homebrew cask auto-updates via upstream PRs (source: https://raw.githubusercontent.com/openai/codex/main/docs/release_management.md).

Conclusions/Next actions
- We now have concrete defaults, event schemas, and sandbox/auth behaviors to mirror in the Neovim plugin (stream parsing for `codex exec`, config options, and health checks for login/API key).
- Execpolicy/prompt discoveries suggest optional integration points: surface policy presence/validation in health checks, and expose user prompt directory shortcuts or `/prompts:<name>` equivalents in Neovim.
- Windows sandbox gaps imply we should caution Windows users or steer them to WSL2; network/write expectations differ by platform.
- Next: reconcile these findings with the current plan, decide how much de `exec` JSON event handling, sandbox/profile toggles, prompts, and execpolicy awareness we expose in la UI/cliente Lua, y mapear MCP server/client capabilities antes de salir de research.
